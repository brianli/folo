超节点这件事，不能再只按”多少张卡”来理解。72 张 Blackwell GPU 如果只放进同一个机柜，它仍然是一台高密服务器；GB200 NVL72 的关键在于这 72 张 GPU 被放进同一个 NVLink domain，机柜内部有 130 TB/s 的 GPU 通信带宽，单 GPU NVLink 双向互联达到 1.8 TB/s[\[1\]](https://www.nvidia.com/en-us/data-center/gb200-nvl72/)[\[2\]](https://developer.nvidia.com/blog/nvidia-gb200-nvl72-delivers-trillion-parameter-llm-training-and-real-time-inference/)。**南向互联的竞争已经上移到系统契约：谁控制事务语义、谁负责管理面、谁能让软件栈真正看见甚至重排 topology——这才是这些卡能不能像一台机器一样工作的真正决定因素。**

把六条路线放进同一张表——NVLink、华为 UB、Google TPU、UALink、SUE/ESUN 和国产路线——会发现它们的 PHY 层在逐步趋同，系统行为却在 data link 的可靠性/流控模型和 transaction layer 的内存语义上彻底分野。NVLink 5.0 单 GPU 1.8 TB/s 仍然领先，UALink 1.0 每 station 只有 800 Gb/s[\[10\]](https://ualinkconsortium.org/wp-content/uploads/2025/04/UALink-1.0-White_Paper_FINAL.pdf)——但 UALink 要管的是 1024 个 accelerator 的开放 pod；Google TPU 干脆不在”谁链路最快”这条轴上较劲，它用光路交换把整张拓扑做成可重排的资源。前期四篇专题深挖分别拆解了 NVLink、SUE、UALink 与 Google TPU 的分层机制[\[33\]](https://miraclefarms.github.io/notes/2026/06/21/nvlink-evolution-from-p100-to-rubin-feynman/)[\[34\]](https://miraclefarms.github.io/notes/2026/06/21/sue-scale-up-ethernet-fabric/)[\[35\]](https://miraclefarms.github.io/notes/2026/06/21/ualink-open-scale-up-fabric/)[\[42\]](https://miraclefarms.github.io/notes/2026/06/22/google-tpu-architecture-evolution-interconnect/)；这篇综述把六条路线合到同一张地图，按三类工程立场重构比较维度，给出可验收的判断。

## 一、NVL72 把 rack 变成了调度原子

> **本节论点**：NVL72 的意义不在”机柜里有 72 张卡”，而在 NVLink domain 成为调度器、通信库和 runtime 共同承认的资源契约；跨出这个域，带宽会出现约三个数量级的断崖。 **本节核心参考**：
> 
> - ★★★ **NVIDIA GB200 NVL72 官方博客**[\[2\]](https://developer.nvidia.com/blog/nvidia-gb200-nvl72-delivers-trillion-parameter-llm-training-and-real-time-inference/) — 72-GPU domain / 130 TB/s / 1.8 TB/s 的一手数字
> - ★★ NVIDIA Multi-Node NVLink Tuning Guide[\[3\]](https://docs.nvidia.com/multi-node-nvlink-systems/multi-node-tuning-guide/overview.html) — 把 NVL72 描述成 model parallelism 的 72-GPU domain
> - ★ 前期调研文章《NVLink 演进史》[\[33\]](https://miraclefarms.github.io/notes/2026/06/21/nvlink-evolution-from-p100-to-rubin-feynman/) — NVLink 代际主线与 one-sided AllToAll

GB200 NVL72 的公开材料给了一个极清楚的参照系：36 个 Grace CPU、72 个 Blackwell GPU、液冷机柜、72-GPU NVLink domain。技术博客拆开第五代 NVLink：每块 Blackwell GPU 有 18 个 NVLink 端口，每端口 100 GB/s，单 GPU 双向 1.8 TB/s，9 个 NVLink switch tray 把 72 张 GPU 接进同一个 130 TB/s 的高带宽域[\[2\]](https://developer.nvidia.com/blog/nvidia-gb200-nvl72-delivers-trillion-parameter-llm-training-and-real-time-inference/)。NVIDIA 把这套体验称为”single, massive GPU”，多节点 NVLink tuning guide 则直接把它写成 model parallelism 的 72-GPU domain[\[3\]](https://docs.nvidia.com/multi-node-nvlink-systems/multi-node-tuning-guide/overview.html)。

![[超节点南向互联：六条路线、三类哲学与系统契约之争-01.png]]

*图 1：NVLink/NVSwitch 的 rack-scale 拓扑示意。真正改变调度语义的是 NVLink domain：调度器应把它看成通信域、故障域和供电/液冷约束共同构成的资源契约，而不是”机柜里有多少张卡”。*

这套架构对训练和推理的压强不同。训练侧受益于 TP/EP/PP/SP 这些并行组不再频繁跨出高速域，all-reduce、all-gather、reduce-scatter、all-to-all 的成本被压在机柜内部。推理侧更直接：MoE 的 expert dispatch/combine、Prefill/Decode 之间的 KV 迁移、长上下文下的 KV cache 放置，都可以围绕 72 卡域重新设计。前期 NVLink 分析里有一个关键证据：TensorRT-LLM 的 one-sided AllToAll 用 CUDA VMM 把同一 NVLink domain 内各 GPU 的物理内存映射进彼此的虚拟地址空间，MoE dispatch kernel 可以像访问本地指针一样读写 peer memory，把”每个 token 该发给谁”下沉到 kernel 和 buffer layout[\[4\]](https://raw.githubusercontent.com/NVIDIA/TensorRT-LLM/main/docs/source/blogs/tech_blog/blog18_Optimizing_MoE_Communication_with_One_Sided_AlltoAll_Over_NVLink.md)。**NVLink domain 已经从一根物理连线，变成 CUDA/NCCL/NVSHMEM/MoE runtime 共同消费的软件资源契约。**

这给项目材料一个很实用的提醒：**“单机柜多少卡”和”单一 scale-up 域多少卡”必须分开写。**一个机柜可以塞 72/128 张卡，但如果它们只是通过普通 RoCE/IB 松散连接，软件看到的仍是 scale-out 集群；只有拓扑发现、rank placement、集合通信库和故障域管理都承认同一个南向互联域，才配叫”像一台机器一样工作”。这个区分有一个很硬的物理背景：NVL72 机柜内 130 TB/s 和跨出 domain 后约 50 GB/s 的 InfiniBand/Ethernet 之间，存在约三个数量级的带宽断崖，而截至 2026 年中没有任何公开路线图能在 2026-2027 年内把它填平[\[33\]](https://miraclefarms.github.io/notes/2026/06/21/nvlink-evolution-from-p100-to-rubin-feynman/)。这意味着调度器一旦把模型并行组切到 domain 边界外，吞吐损失会以数量级计——这是切错位置的真实代价。

## 二、华为 UB 路线把 CPU、NPU 和内存都拉进同一个南向域

> **本节论点**：华为 UB 把南向互联的作用从 collective communication 扩展到了 memory fabric——KV cache、权重、checkpoint 都能放进可被所有 NPU 访问的分布式内存池。这给国产超节点的指标设定提出了 NVLink 之外的新维度。 **本节核心参考**：
> 
> - ★★★ **CloudMatrix384 论文**[\[9\]](https://arxiv.org/html/2506.12708v1) — UB/RDMA/VPC 三平面、跨节点退化率与 EMS 内存池的一手数据
> - ★★ 华为徐直军全联接大会主旨演讲[\[8\]](https://www.huawei.com/cn/news/2025/9/hc-xu-keynote-speech) — Atlas 900/950/960 超节点规模路线
> - ★ 前期调研文章《NVLink 演进史》[\[33\]](https://miraclefarms.github.io/notes/2026/06/21/nvlink-evolution-from-p100-to-rubin-feynman/) — NVLink symmetric memory 作为专有闭环对照

华为在 2025 年全联接大会上把”超节点”讲得更激进。Atlas 900 满配 384 张 Ascend 910C，CloudMatrix384 是华为云基于 Atlas 900 构建的实例；后续 Atlas 950 规划 8192 张 Ascend 950DT、160 个机柜、柜间全光互联、16 PB/s 级互联带宽，Atlas 960 进一步规划到 15488 卡和 34 PB/s[\[8\]](https://www.huawei.com/cn/news/2025/9/hc-xu-keynote-speech)。这些数字有很强的发布会表达色彩，写正式材料时需要标明来源和上市时间；但方向很明确：用大规模互联域弥补单芯片制程和单卡性能差距。

CloudMatrix384 论文给了比发布会更可分析的结构。它由 384 个 Ascend 910C NPU 和 192 个 Kunpeng CPU 组成，内部有三张平面：UB plane 承载超节点内高带宽低延迟 scale-up，RDMA plane 承载跨超节点 scale-out，VPC plane 负责数据中心网络与控制流[\[9\]](https://arxiv.org/html/2506.12708v1)。论文里的关键数据是：跨节点 NPU-NPU read 带宽 164 GB/s，节点内 167 GB/s，退化不到 3%；512B read 延迟跨节点 1.9 微秒、节点内 1.2 微秒，延迟增加不到 1 微秒[\[9\]](https://arxiv.org/html/2506.12708v1)。

![[超节点南向互联：六条路线、三类哲学与系统契约之争-02.png]]

*图 2：CloudMatrix384 把 UB、RDMA、VPC 三类流量拆成不同平面。UB 负责超节点内 NPU/CPU 的内存语义互联，RDMA 负责 scale-out，VPC 负责控制和数据中心接入。来源：CloudMatrix384 论文 Figure 2 子图。*

“384 比 72 大很多”只是表面比较，UB 对软件栈形状的改变更关键。论文把 UB 描述成可让 NPU 和 CPU 直接 P2P 访问的高带宽平面，并用 EMS（Elastic Memory Service）把 CPU-attached DRAM 组织成可被所有 NPU 访问的分布式内存池；KV cache、模型权重块、checkpoint 和 context cache 都可以放进这个池，再由 Prefill/Decode 节点按需取用[\[9\]](https://arxiv.org/html/2506.12708v1)。换句话说，华为路线把南向互联的作用从 collective communication 扩展成了 memory fabric——这恰好和 NVLink 经由 NVSHMEM/CUDA VMM 暴露远端内存语义的方向同构，只是华为把 CPU、DRAM 也一起拉进了这个域[\[33\]](https://miraclefarms.github.io/notes/2026/06/21/nvlink-evolution-from-p100-to-rubin-feynman/)。

**这对国产超节点指标设定很关键：只测 all-reduce 带宽不够，必须同时测 KV block Put/Get、远端 DRAM 访问、模型加载时间和 P/D 之间的 KV 迁移。**论文里给出过一个很有说服力的数字：在 context caching 命中率提升后，EMS with UB 在 90% token reuse 下把 TTFT 降低 1505ms（59%），且 UB 访问相对 VPC 访问带来更低 TTFT[\[9\]](https://arxiv.org/html/2506.12708v1)。如果软件栈不能把这些流量类型区分出来，高带宽 fabric 最终会在 P99 延迟里变成排队噪声。

## 三、Google TPU 把”拓扑”做成可调度资源

> **本节论点**：TPU 给南向互联引入了 NVLink/UB 闭环和 UALink/SUE 开放之外的第三种工程立场——同样是垂直闭环，赌注却从”单链路最快”或”协议最开放”换成”拓扑可重构”：用光路交换（OCS）把互联拓扑本身做成可重排、可调度的资源，并按训练/推理把拓扑直接分叉。 **本节核心参考**：
> 
> - ★★★ **TPU v4: An Optically Reconfigurable Supercomputer for ML**[\[39\]](https://arxiv.org/abs/2304.01433) 与 **TPU 8t/8i 架构 deep dive**[\[40\]](https://cloud.google.com/blog/products/compute/tpu-8t-and-tpu-8i-technical-deep-dive) — OCS 可重构 3D torus 与 Boardfly 低直径拓扑的一手口径
> - ★★ NSDI 2024《Resiliency at Scale: Managing Google’s TPUv4 ML Supercomputer》[\[41\]](https://www.usenix.org/system/files/nsdi24-zu.pdf) — 6144 条 optical ICI links / 48 个 OCS / 单一 ICI domain 的系统数据
> - ★ 前期调研文章《Google TPU 架构演进》[\[42\]](https://miraclefarms.github.io/notes/2026/06/22/google-tpu-architecture-evolution-interconnect/) — 代际主线与 ICI/DCN 两级集群

把 NVLink 和 UALink 摆在一起，很容易得出一个印象：scale-up 就是”把更多卡用更快的链路全互连进一个大而平的域”。Google TPU 给的是另一个答案。从 v4 开始，TPU 的 Pod 不再是一次性焊死的布线，而是一组可以在作业开始前或故障恢复时被光路交换重排的互联资源。

v4 论文把这件事讲得很克制：OCS 用不到 5% 的系统成本、不到 3% 的功耗，给整个超算引入可重构光互联[\[39\]](https://arxiv.org/abs/2304.01433)。NSDI 2024 的 resiliency 论文把结构补全：v4 以 4x4x4 cube 为资源单元，每个 cube 的六个方向暴露光 ICI 链路，再由 Palomar OCS 拼成更大的 3D torus 或 twisted torus；一个 v4 supercomputer 有 64 个 cube、6144 条 optical ICI links 和 48 个 OCS，整个 Pod 是单一 ICI domain，任意 TPU 之间可 RDMA[\[41\]](https://www.usenix.org/system/files/nsdi24-zu.pdf)。**OCS 不是普通分组交换机，它是电路交换：在作业开始或恢复时改变光链路的连接关系，让同一批物理 cube 组成不同的逻辑拓扑。**这一个机制同时缓解四类问题——按作业分配不同大小/形状的 slice、用 twisted torus 抬高特定形状的 bisection（4x4x8 twisted 相比非 twisted 理论 bisection 提升约 70%）、绕开坏链路或坏 cube、把新硬件增量接入而不必整柜停机重布线[\[39\]](https://arxiv.org/abs/2304.01433)。

![[超节点南向互联：六条路线、三类哲学与系统契约之争-03.png]]

*图 3：TPU 8i 的 Boardfly 拓扑——4 芯片 building block、8 板全连接 group、36 个 group 经 OCS 互连。它把 1024 芯片 Pod 的最大网络直径从 8x8x16 三维 torus 的 16 跳压到 7 跳（约 56%）。这正是”拓扑可调度”落到推理负载上的形态：拓扑形状由 all-to-all 通信模式反向决定，而不是反过来。来源：Google Cloud Blog TPU 8t/8i deep dive。*

TPU 把这种”拓扑可调度”的立场一路推到第八代，并且按 workload 把拓扑分叉。8t 面向大规模 pre-training，继续扩大 3D torus，再叠一层 Virgo scale-out fabric：Google 称 Virgo 用 high-radix switches、flat two-layer non-blocking topology，单 fabric 可连接超过 134,000 个 TPU 8t chip，non-blocking bisection 最高 47 petabits/s，配合 JAX 和 Pathways 把训练扩到超过 100 万 chip 的 logical cluster[\[40\]](https://cloud.google.com/blog/products/compute/tpu-8t-and-tpu-8i-technical-deep-dive)。8i 面向 reasoning/serving，则没有继续把 3D torus 当默认答案，而是改用上面那张 Boardfly：dense training 的规整邻居 reduction 适合 torus，MoE/reasoning 的 all-to-all 更怕长直径，于是用 OCS 把拓扑重排成低直径形态。**TPU 8t/8i 是目前最硬的一条证据：workload pattern 已经强到可以反向决定网络拓扑——训练要吞吐、同步和容错，推理要低尾延迟、MoE 路由和 KV locality，两者不再共用一张拓扑假设。**

这对超节点的判断有两个增量。其一，**OCS 给”带宽断崖”提供了一条不同于抬高跨域带宽的解法：与其把跨出域之后的地板从 50 GB/s 往上挪，不如把域内拓扑重排成贴合作业的形状。**调度器手里因此多了一层自由度——拓扑从焊死的固定布线变成可被作业塑形的互联资源池。其二，TPU 的可调度性建立在”芯片、ICI、OCS、XLA/GSPMD、Pathways 全栈自研”之上，因此它是一种比 NVLink 更彻底的垂直闭环——代价是它只在 Google Cloud 内可用，不对外售卖芯片，开放生态从一开始就不在它的目标函数里。对国产或开放路线，OCS 本身难以照搬，真正能借走的是”把拓扑当成可调度资源、按训练/推理分叉”这个系统视角。

## 四、六条路线，三类哲学

> **本节论点**：把六条路线压成一句话——NVLink、华为 UB、Google TPU 都是垂直闭环但各押不同机制（最快内存 fabric / CPU-NPU-内存池 / 可重构光路交换），UALink 是开放专用协议，SUE/ESUN 是以太网交换生态向 rack-scale 内存事务域下沉，国产以太网 scale-up 则在用国产交换芯片绕开私有互连依赖。它们的核心赌注不同，强项和短板也随之不同。 **本节核心参考**：
> 
> - ★★★ **前期调研文章《UALink 综述》**[\[35\]](https://miraclefarms.github.io/notes/2026/06/21/ualink-open-scale-up-fabric/) 与 **《SUE 综述》**[\[34\]](https://miraclefarms.github.io/notes/2026/06/21/sue-scale-up-ethernet-fabric/) — 开放路线的协议与生态拆解
> - ★★ AMD: Delivering Open Rack Scale AI Infrastructure[\[15\]](https://www.amd.com/en/blogs/2025/amd-delivering-open-rack-scale-ai-infrastructure-to-unlock-agentic-ai.html) — Helios 把 UALink 落进 72 GPU rack
> - ★ UALink 1.0 白皮书[\[10\]](https://ualinkconsortium.org/wp-content/uploads/2025/04/UALink-1.0-White_Paper_FINAL.pdf) — 开放 pod 的规格上限

南向互联看起来是六家在比拼，背后是三类工程立场在博弈。前两类沿”谁拥有 fabric”分野，第三类则把赌注换到了”fabric 用什么机制”这条轴上。

第一类是**垂直闭环 + 分组交换的全互连/内存 fabric**：NVLink 和华为 UB。硬件、互联、交换芯片、通信库、运行时一起设计，软件能吃到最强的专有语义。NVLink 由 NVIDIA 把 CUDA、NCCL、NVSHMEM、CUDA VMM、TensorRT-LLM 一起对齐；UB 由华为把 Ascend、Kunpeng、CANN、HCCL、EMS 一起对齐。闭环的代价是生态绑定，收益是确定的性能和可预测的软件体验。

第二类是**垂直闭环 + 可重构光路交换**：Google TPU。它在”全栈自研”这点上比 NVLink 更彻底，赌注却押在拓扑而非单链路带宽——用 OCS 让拓扑可重排、按训练/推理分叉（上一节已展开）。它和第一类共享”闭环”标签，却把主要可调度对象从带宽换成了拓扑，因此单列一类工程立场。

第三类是**开放路线**，内部又分两支。UALink 走开放专用协议：借用 Ethernet 物理层生态，但从 data link 和 transaction layer 开始重新定义 memory-semantic fabric，目标是把 1024 个 accelerator 组织成一个可被多厂商软件、管理面和采购体系共同识别的 pod[\[10\]](https://ualinkconsortium.org/wp-content/uploads/2025/04/UALink-1.0-White_Paper_FINAL.pdf)。SUE/ESUN 则更贴近交换芯片厂商的思路：保留 Ethernet 合规性，用更小的头部、链路层重传和低时延交换芯片，把以太网短路径改造成 scale-up pod，很多上层内存语义仍留给 XPU 厂商自己掌握[\[34\]](https://miraclefarms.github.io/notes/2026/06/21/sue-scale-up-ethernet-fabric/)。AMD Helios 是这条开放路线最明显的系统级承接者：它通过 UALink 让 72 个 GPU 在 rack 内扩展，同时支持 UAL over Ethernet[\[15\]](https://www.amd.com/en/blogs/2025/amd-delivering-open-rack-scale-ai-infrastructure-to-unlock-agentic-ai.html)。

![[超节点南向互联：六条路线、三类哲学与系统契约之争-04.webp]]

*图 4：NVIDIA Vera Rubin POD 把 NVLink、Spectrum-X Ethernet、storage 和 CPU 机架组织成 pod 级系统。这张图说明垂直闭环路线的产品形态已经外扩到多 rack-scale system 协同，而不只是单机柜——开放路线要追的正是这种”系统级可用性”，而非单链路带宽。来源：NVIDIA Vera Rubin POD 官方博客。*

把六条路线放进同一张表，比较对象就清楚了：

| 路线                | 核心赌注                                   | 强项                                                     | 短板                              |
| ----------------- | -------------------------------------- | ------------------------------------------------------ | ------------------------------- |
| NVLink / NVSwitch | 垂直整合：GPU、switch、CUDA/NCCL/NVSHMEM 一起设计 | 单卡带宽最高，NVL72/NVL576 已产品化，软件直接吃硬件语义                     | 生态绑定强，按流量分级 QoS 仍不透明            |
| 华为 UB             | NPU/CPU/内存池一体化闭环                       | CPU/NPU/内存语义统一，已有 KV/EMS 生产论文                          | 公开生态与跨厂商互操作有限，多数指标依赖厂商材料        |
| Google TPU / OCS  | 全栈自研闭环 + 光路交换可重构拓扑                     | 拓扑随作业重排、OCS 容错与碎片治理、训练/推理拓扑分叉（8t torus vs 8i Boardfly） | 仅 Google Cloud 内可用，不对外售卖芯片，生态封闭 |
| UALink            | 开放 memory-semantic pod 标准              | 协议层定义 read/write/atomic 与 1024-accelerator pod         | 交换芯片与互操作仍在 2026-2027 验证期        |

| 国产以太网 scale-up    | 用国产以太网交换替代 NVIDIA 私有 IB                | 绕开私有互连依赖，宣称单卡带宽已达 NVLink 量级                            | 多为厂商设计目标，缺公开实测                  |

## 五、Memory-semantic 是开放路线的分水岭

> **本节论点**：UALink 和 SUE 都借用 Ethernet PHY 生态，但 UALink 从协议层把 read/write/atomic、57-bit 地址空间和 1024-accelerator pod 写成标准，SUE 把内存语义留给 XPU 厂商。这条分界决定了”开放”到底开放到哪一层。 **本节核心参考**：
> 
> - ★★★ **UALink 200G 1.0 Specification Overview**[\[12\]](https://ualinkconsortium.org/blog/ualink-200g-1-0-specification-overview-802/) 与 **UALink 2026 白皮书**[\[11\]](https://ualinkconsortium.org/wp-content/uploads/2026/01/UALink_White_Paper_Publication_FINAL_UPDATED.pdf) — read/write/atomic、57-bit 地址、1024 pod、93% 有效带宽目标
> - ★★ HPE Helios 公告[\[16\]](https://www.hpe.com/us/en/newsroom/press-release/2025/12/hpe-accelerates-ai-deployments-with-first-amd-helios-ai-rack-scale-architecture-with-open-scale-up-networking-built-with-broadcom.html) — Helios 落到 OEM 形态的混合实现
> - ★ 前期调研文章《SUE 综述》[\[34\]](https://miraclefarms.github.io/notes/2026/06/21/sue-scale-up-ethernet-fabric/) — SUE 的 opaque command channel

UALink 不是给 RDMA 换个名字。官方概览明确写到，它支持 memory semantics：read、write、atomic；transaction 粒度 64 到 256 字节；地址空间是 vendor-defined 的 57-bit physical address space；路由 source/destination-based，支持最多 1024 endpoints[\[12\]](https://ualinkconsortium.org/blog/ualink-200g-1-0-specification-overview-802/)。这些词放在一起，说明 UALink 要让 accelerator 对 accelerator 直接发起内存事务，而不是让 host CPU 或传统 NIC 成为所有数据移动的中心。2026 白皮书把它收敛成一套可量化目标：deterministic、lossless 的 switched pod，93% effective bandwidth target，sub-microsecond RTT，link-layer processing 数百纳秒，copper under four meters[\[11\]](https://ualinkconsortium.org/wp-content/uploads/2026/01/UALink_White_Paper_Publication_FINAL_UPDATED.pdf)。

![[超节点南向互联：六条路线、三类哲学与系统契约之争-05.png]]

*图 5：UALink switched pod 示例。多个 OS domain 通过 UALink switch 形成 scale-up pod，上限指向 1024 accelerator。pod 不只是物理拓扑，它要同时承接主机、accelerator、交换机和管理面的边界——这正是 UALink 把”内存语义”写进标准的原因。来源：UALink 白皮书。*

SUE 的选择恰好相反。它定义的是 XPU 之间 load/store/single-sided memory operations over Ethernet 的 transport；XPU command 的操作码、读写语义、是否映射成 put/get/atomic，由 XPU 自己定义，SUE 只看 remote XPU identifier、VC、控制长度和数据长度，其余控制位多作为 opaque payload 送到远端[\[34\]](https://miraclefarms.github.io/notes/2026/06/21/sue-scale-up-ethernet-fabric/)。**SUE 开放的是 fabric 承载方式，XPU 微架构仍由各家掌握；UALink 开放的是 fabric 加上内存事务语义。**这里没有谁天然更优，只有集成点不同：UALink 未来互操作目标更强，SUE 换来更小的 IP 面积和实现自由度——对已经有自家 XPU NOC 和 memory model 的厂商，SUE 的 opaque command channel 反而更容易接进去。

这条分水岭在 AMD Helios 的落地形态里看得最清楚。HPE 把 Helios 做成 OEM 产品：72 个 AMD Instinct MI455X GPU，每 rack 260 TB/s aggregate scale-up bandwidth、2.9 AI exaflops FP4、31 TB HBM4，并强调与 Broadcom 合作的标准 Ethernet scale-up switch[\[16\]](https://www.hpe.com/us/en/newsroom/press-release/2025/12/hpe-accelerates-ai-deployments-with-first-amd-helios-ai-rack-scale-architecture-with-open-scale-up-networking-built-with-broadcom.html)。它的公开表述同时出现 UALink、UAL over Ethernet 和 Broadcom scale-up Ethernet switch[\[15\]](https://www.amd.com/en/blogs/2025/amd-delivering-open-rack-scale-ai-infrastructure-to-unlock-agentic-ai.html)。**这说明真实产品大概率是个混合体：UALink 事务语义、Ethernet-derived fabric、Broadcom switch 和 AMD GPU 拼成一台机器，教科书式的”纯 UALink pod”反而少见。对买方而言，规范名称没有”72 GPU 能否被通信库、runtime 和调度器当成一个稳定 scale-up domain”重要。**

## 六、PHY 趋同，DL/TL 分裂：标准之争发生在哪一层

> **本节论点**：开放 scale-up 标准很少从 SerDes 层分道扬镳。同一代 AI rack 的最底层大概率共用相似的 PAM4 SerDes 和光模块，系统行为却因 data link 的可靠性/流控模型和 transaction layer 的内存语义而完全不同。 **本节核心参考**：
> 
> - ★★★ **UALink 200G 1.0 Specification Overview**[\[12\]](https://ualinkconsortium.org/blog/ualink-200g-1-0-specification-overview-802/) 与 **OCP《Scale Up Ethernet》v1.0.0**[\[17\]](https://www.opencompute.org/documents/ocp-sue-spec-final-pdf-1) — 两条路线的 TL/DL/PHY 分层
> - ★★ Synopsys ESUN/SUE/UALink 概览[\[20\]](https://www.synopsys.com/articles/ethernet-standards-scale-up-ai.html) — 三套开放标准的分工
> - ★ UEC 1.0 白皮书[\[37\]](https://ultraethernet.org/wp-content/uploads/sites/20/2025/06/UEC1.0Whitepaper.pdf)；Broadcom OFC 2026 portfolio[\[38\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-showcases-industry-leading-solutions-scaling-ai)（OCI MSA 光互连）

把南向互联粗略拆成 PHY/PL/DL/TL 四层，SUE 和 UALink 的差异就不再是”谁用不用以太网物理层”这么简单。UALink 公开概览写得很直白：Transaction Layer 管 credits 和 TL flit packing/unpacking；Data Link Layer 在 TL 和 Physical Layer 之间搬运数据；Physical Layer 包含 PCS，并基于 IEEE P802.3dj draft 复用 Ethernet 技术再按需调整[\[12\]](https://ualinkconsortium.org/blog/ualink-200g-1-0-specification-overview-802/)。也就是说，UALink 在 SerDes 层不另起炉灶，它从 DL/TL 开始把通用 packet network 改成 accelerator memory-semantic fabric。SUE 的路径不同：它仍把每个 PDU 映射成一个 Ethernet packet，链路侧用 FEC、LLR、PFC/CBFC 提供 lossless 行为，transport 层处理 per-destination/VC packing 和可靠传输[\[17\]](https://www.opencompute.org/documents/ocp-sue-spec-final-pdf-1)。

![[超节点南向互联：六条路线、三类哲学与系统契约之争-06.png]]

*图 6：UALink 四层协议栈。Physical Layer 复用 Ethernet PHY 方向，Protocol/Transaction/Data Link 三层则面向 accelerator memory fabric 重新定义事务、credit、flit 和链路行为。这张图解释了为什么 UALink 和 SUE 常被放在一起，却不应混成一类。来源：UALink 白皮书。*

![[超节点南向互联：六条路线、三类哲学与系统契约之争-07.png]]

*图 7：SUE 白皮书的 64 XPU 单跳交换部署示例。每个 XPU 通过多个 800G SUE instance 接入多平面交换芯片，任意两 XPU 的带宽来自多个平面叠加。SUE 的分野发生在 Ethernet 内部——保留交换芯片和运维生态，但把 header、flow control、link retry 和 transport scheduling 都向 scale-up 事务压缩。来源：OCP SUE 白皮书 Figure 1。*

把几条主线放进同一张分层表，会看到一个反直觉的结构：

| 路线          | PHY / PMD / PMA                         | PL / PCS / RS                    | DL                                 | TL / Protocol                                    |
| ----------- | --------------------------------------- | -------------------------------- | ---------------------------------- | ------------------------------------------------ |
| SUE / ESUN  | Ethernet PHY / 200G SerDes              | Ethernet 兼容，配合 AFH 与低时延 FEC      | LLR、PFC/CBFC、lossless class        | SUE-T transport，XPU command 多数 opaque            |
| UEC         | Ethernet PHY                            | Ethernet PHY/PCS 演进              | AI/HPC congestion signaling、CBFC   | UET，advanced RDMA、multipath、selective retransmit |
| UALink      | 基于 IEEE P802.3dj 的 Ethernet-derived PHY | 为 flit/codeword 对齐与低时延 replay 适配 | UALink flit、CRC、link replay、credit | UPLI/TL，load/store/atomic 与 memory semantics     |
| CXL         | PCIe PHY                                | PCIe PL 之上扩展                     | CXL.io 与 CXL.cache/mem link        | CXL.io / CXL.cache / CXL.mem                     |
| NVLink / UB | 厂商自定义                                   | 厂商自定义                            | 厂商自定义                              | 厂商自定义 memory fabric + collective/runtime 协同      |

这张表解释了为什么”南向互联总线标准”会看起来都像四层栈，却不在同一层竞争。PHY 层竞争 lane rate、reach、功耗、BER、封装和光电转换；DL 层竞争 replay 粒度、credit、deadlock avoidance、lossless class；TL 层竞争 load/store/atomic、memory ordering、collective、地址空间和 endpoint/switch 协同。**同一代 AI rack 里，最底层可能都在用相似的 SerDes 和光模块，系统行为却会因为 DL/TL 语义完全不同。**

这条趋势在物理层还会被进一步推平。OCI MSA 关注的是开放 optical scale-up interconnect 规格，目标是让 AI scale-up 从 copper 逐步走向 silicon-centric optics，并让 XPU 和 switch 匹配多供应商光技术[\[38\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-showcases-industry-leading-solutions-scaling-ai)。它不替上层选择 UALink、SUE 还是私有协议，只想把最贵、最难量产的 optical PHY 先标准化。后续标准竞争大概率是”双层战场”：底层光电接口尽量开放，上层 memory fabric 继续分化。

**（v3.0 更新）** 这里要把”光”在 scale-up 里的两种用法分清楚，否则容易把 OCI MSA 和 Google OCS 混为一谈。OCI MSA、CPO、Celestial AI 这一类做的是 point-to-point 的光收发：把同一条链路做得更快、更长、更省电，本质仍是把 copper PHY 换成 optical PHY，拓扑还是焊死的[\[38\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-showcases-industry-leading-solutions-scaling-ai)。Google 的 OCS 是另一种用法：光被做成一台可重排连接关系的电路交换机，链路速度反倒是次要的，拓扑因此从静态布线变成可调度资源[\[39\]](https://arxiv.org/abs/2304.01433)。**两者都靠光突破 copper 的距离/带宽墙，但一个抬高链路上限、一个抬高拓扑自由度——前者落在 PHY 层，后者直接改变了”域”的可塑性。**对超节点选型，这意味着评估光互连不能只问”单纤多少 Tb/s”，还要问”这套光层是固定点对点，还是可以在作业间重排拓扑”。

## 七、In-Network Compute：所有路线都在把 collective 推进 fabric

> **本节论点**：把 AllReduce/AllGather/Broadcast 从 endpoint 反复搬运改成在交换芯片内执行，是所有 scale-up 路线的共同方向——NVSwitch SHARP、Tomahawk Ultra、UALink Common 2.0、Astera Hypercast 在做同一件事。 **本节核心参考**：
> 
> - ★★★ **UALink 2026 年 4 月四规格公告**[\[14\]](https://www.businesswire.com/news/home/20260407620696/en/Ultra-Accelerator-Link-UALink-Consortium-Publishes-Four-Specifications-Defining-In-Network-Compute-Chiplets-Manageability-and-200G-Performance) 与 **Broadcom Tomahawk Ultra**[\[18\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-ships-tomahawk-ultra-reimagining-ethernet-switch-hpc) — In-Network Compute / in-network collectives 的两条一手口径
> - ★★ Astera Scorpio X-Series[\[23\]](https://www.asteralabs.com/news/astera-labs-extends-leadership-in-open-ai-scale-up-networking-with-new-320-lane-scorpio-x-series-smart-fabric-switch/) — Hypercast 与 In-Network Compute engines
> - ★ 前期调研文章《NVLink 演进史》[\[33\]](https://miraclefarms.github.io/notes/2026/06/21/nvlink-evolution-from-p100-to-rubin-feynman/) — NVSwitch SHARP 的先例

collective 不是边角料，它是 scale-up fabric 的热路径。MoE dispatch/combine、AllReduce、AllGather、Broadcast 这些操作如果一直由 endpoint 反复搬运，GPU 利用率会死在 fabric 上。NVIDIA 早在 Hopper 一代就给出了答案：第三代 NVSwitch 引入 SHARP，在 fabric 内部做 reduction 和 multicast[\[33\]](https://miraclefarms.github.io/notes/2026/06/21/nvlink-evolution-from-p100-to-rubin-feynman/)。NCCL 2.27 之后把 symmetric memory、NVLink/IB SHARP 进一步显式暴露给集体通信[\[5\]](https://developer.nvidia.com/blog/enabling-fast-inference-and-resilient-training-with-nccl-2-27/)。

开放路线在追同一个方向。Broadcom Tomahawk Ultra 声称可以在交换芯片内执行 AllReduce、Broadcast、AllGather，减轻 XPU 负担并改善 job completion time[\[18\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-ships-tomahawk-ultra-reimagining-ethernet-switch-hpc)。UALink 2026 年 4 月的 Common 2.0 直接引入 In-Network Compute，用于在 accelerator 之间融合计算和通信，官方目标是降低延迟、节省带宽、提升 scaling efficiency[\[14\]](https://www.businesswire.com/news/home/20260407620696/en/Ultra-Accelerator-Link-UALink-Consortium-Publishes-Four-Specifications-Defining-In-Network-Compute-Chiplets-Manageability-and-200G-Performance)。merchant switch 一侧，Astera Scorpio X-Series 给出 Hypercast 和 In-Network Compute engines，按其内部分析口径可把 collective 操作提升到最高 2x[\[23\]](https://www.asteralabs.com/news/astera-labs-extends-leadership-in-open-ai-scale-up-networking-with-new-320-lane-scorpio-x-series-smart-fabric-switch/)。

**（v3.0 新增）** Google TPU 在同一个方向上给了一个 endpoint 侧的变体。8i 用 Collectives Acceleration Engine（CAE）替代上一代 SparseCore，官方说法是可把 on-chip collective latency 降低最多 5 倍；前几代的 SparseCore 则用约 5% die/power 把 embedding-heavy 模型的通信-计算融合下沉到芯片[\[40\]](https://cloud.google.com/blog/products/compute/tpu-8t-and-tpu-8i-technical-deep-dive)。它和 NVSwitch SHARP、Tomahawk Ultra 把 reduction 放进交换芯片的思路略有不同——CAE 更靠近 accelerator 端而非中央 switch——但解决的是同一个问题：把不规则 collective 从 endpoint 反复搬运中解放出来。**这进一步说明 In-Network/near-fabric collective 已经从某一条路线的专利变成每条路线都要回答的题，区别只在于各自把加速逻辑放在了 switch、协议层还是 accelerator 端。**

**这意味着 In-Network Compute 已经从 NVIDIA 的专有优势变成所有 scale-up 路线的共识门槛。**对项目材料的提醒是：评估一条 fabric 不能只问”支不支持 in-network collectives”，要问它覆盖哪些 primitive、对 MoE dispatch/combine 这类不规则通信是否有效、能否被通信库稳定调用、有没有可复现 benchmark。把 collective 推进 switch 是方向，但”宣称支持”和”软件能用上”之间隔着整条通信库适配链。

## 八、交换芯片供应链：Broadcom 主押以太网，UALink 是期权

> **本节论点**：标准之争的另一面是交换芯片供应链。截至 2026 年中，Broadcom 公开路线压在 Ethernet（Tomahawk 6 / Ultra / Thor Ultra），把 UALink 当期权；UALink switch 的直接进攻方更像 Astera 和 Marvell/XConn。 **本节核心参考**：
> 
> - ★★★ **Broadcom Tomahawk 6**[\[21\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-ships-tomahawk-6-worlds-first-1024-tbps-switch) 与 **Tomahawk Ultra**[\[18\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-ships-tomahawk-ultra-reimagining-ethernet-switch-hpc) — Broadcom 的 scale-up/scale-out 分层口径
> - ★★ Astera Scorpio X-Series[\[23\]](https://www.asteralabs.com/news/astera-labs-extends-leadership-in-open-ai-scale-up-networking-with-new-320-lane-scorpio-x-series-smart-fabric-switch/) 与 Marvell 收购 XConn[\[24\]](https://investor.marvell.com/news-events/press-releases/detail/1004/marvell-to-acquire-xconn-technologies-expanding-leadership-in-ai-data-center-connectivity) — UALink switch 的进攻方
> - ★ Broadcom Thor Ultra[\[22\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-introduces-industrys-first-800g-ai-ethernet-nic) — 800G UEC-compliant NIC

规格之外，谁能交付交换芯片才决定路线能否落地。Broadcom 的公开产品叙事明显压在 Ethernet 侧。Tomahawk 6 是 102.4 Tbps Ethernet switch，官方同时写 scale-up 和 scale-out，给出 512 XPU scale-up cluster、100,000+ XPU two-tier scale-out、100G/200G SerDes、CPO option 和 Cognitive Routing 2.0[\[21\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-ships-tomahawk-6-worlds-first-1024-tbps-switch)。Tomahawk Ultra 把 51.2 Tbps、250ns、64B line-rate、LLR/CBFC 和 in-network collectives 做成低时延 scale-up 特化 SKU[\[18\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-ships-tomahawk-ultra-reimagining-ethernet-switch-hpc)。Thor Ultra 再补上 UEC-compliant 800G NIC：packet-level multipathing、out-of-order delivery、selective retransmission、可编程拥塞控制[\[22\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-introduces-industrys-first-800g-ai-ethernet-nic)。**Broadcom 统一的是 Ethernet 生态和工具链，分化的是 ASIC 微架构：高带宽 Tomahawk 6 主线服务 scale-out 并兼顾部分 scale-up，Ultra 分支把极致 scale-up 的延迟和小包路径单独拉出来。**

UALink switch 的直接进攻方更像 Astera 和 Marvell。Astera 在 2026 年 5 月发布 Scorpio X-Series 320 Lane Smart Fabric Switch，称其是 open, memory-semantic fabric switch，已 shipping to leading hyperscalers，生产爬坡目标在 2026 下半年[\[23\]](https://www.asteralabs.com/news/astera-labs-extends-leadership-in-open-ai-scale-up-networking-with-new-320-lane-scorpio-x-series-smart-fabric-switch/)。Marvell 在 2026 年初收购 XConn 时明说，交易会扩充自己的 UALink scale-up switch team，并把 PCIe/CXL switching IP 与 UALink 机会连接起来[\[24\]](https://investor.marvell.com/news-events/press-releases/detail/1004/marvell-to-acquire-xconn-technologies-expanding-leadership-in-ai-data-center-connectivity)。

Broadcom 没有理由完全放弃 UALink——它仍在会员名单里，也具备 SerDes、retimer、switch ASIC 和 chiplet/IP 能力。但当前公开信号指向一个清晰的优先级：**Broadcom 把 UALink 当期权，把 Ethernet scale-up 当主线产品。**这符合它的商业激励：SUE/ESUN/UEC 能最大化复用 Tomahawk、Thor、optics 和 SONiC/OEM/ODM 生态，全力押 UALink 会削弱”以太网已经足够进入 scale-up”的产品叙事。这个判断有一个边界：若 UALink 在 2026-2027 年通过 AMD Helios、自研 XPU 或 hyperscaler 平台形成真实出货，并且软件能稳定消费 memory-semantic fabric，Broadcom 的期权价值会上升；若系统厂商更看重统一运维和交换芯片现货，Tomahawk 这条线会先吃到规模化部署。

## 九、国内厂商的超节点形态战

> **本节论点**：国产超节点已从”有没有卡”进入”南向互联、通信库、软件迁移、应用验证能不能同时交付”；公开材料必须按证据等级使用，新出现的信号是”用国产以太网交换替代 NVIDIA 私有 InfiniBand”。 **本节核心参考**：
> 
> - ★★★ **沐曦《超节点技术体系白皮书》**[\[26\]](https://www.metax-tech.com/ndetail/12573.html) 与 **昆仑芯北京方案**[\[27\]](https://www.kunlunxin.com/news/4791.html) — 官网可引用的产品形态
> - ★★ 百度天池超节点报道[\[28\]](https://m.mp.oeeee.com/a/BAAFRD0000202511131472482.html)、摩尔线程路线图[\[29\]](https://www.stcn.com/article/detail/3550271.html) — 媒体口径，需标注待确认
> - ★ 寒武纪思元 370[\[31\]](https://www.cambricon.com/index.php?a=lists&c=index&catid=360&m=content)、天数智芯[\[30\]](https://cn.wicinternet.org/2026-01/12/content_38531570.htm) — 软件栈与多芯互连旁证

国内厂商材料的公开程度差异很大，需要分层使用。沐曦是目前公开形态最完整的一类：官方新闻明确列出耀龙 S8000 G2 的 64 张曦云 C550 GPU 3D Mesh 超节点，小数据量通信场景性能提升 4 倍以上；Shanghai Cube 单柜 128 GPU、8 柜组成千卡集群；曦云 C500X 光互连超节点支持 16 至 64 GPU 灵活扩展[\[26\]](https://www.metax-tech.com/ndetail/12573.html)。昆仑芯更谨慎：P800 OAM 按 OCP-OAM 标准设计，支持主流大模型，并通过 IB 或 RoCE 构建万卡级集群[\[27\]](https://www.kunlunxin.com/news/4791.html)；媒体报道称百度规划天池 256 和天池 512 超节点，最高分别支持 256、512 卡互联[\[28\]](https://m.mp.oeeee.com/a/BAAFRD0000202511131472482.html)，这类路线图可作竞品跟踪线索，但要区分”官方已披露”和”媒体报道”。

## 十、训练指标和推理指标要分开设

> **本节论点**：scale-up fabric 的验收不在链路表格里，而在训练 step time、推理 TPOT 和故障恢复窗口里。推理侧最该测的是 KV/EP 争用造成的尾延迟，而不是平均带宽。 **本节核心参考**：
> 
> - ★★★ **CloudMatrix384 论文**[\[9\]](https://arxiv.org/html/2506.12708v1) 与 **OCP《Scale Up Ethernet》v1.0.0**[\[17\]](https://www.opencompute.org/documents/ocp-sue-spec-final-pdf-1) — 推理 KV/EMS 与端点/链路指标的一手口径
> - ★★ Broadcom Tomahawk Ultra[\[18\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-ships-tomahawk-ultra-reimagining-ethernet-switch-hpc) — 交换芯片层的延迟/小包/lossless 基线
> - ★ 前期调研文章《UALink 综述》[\[35\]](https://miraclefarms.github.io/notes/2026/06/21/ualink-open-scale-up-fabric/) — 六层验收框架

训练场景的南向互联指标，主线是把模型并行域稳定扩到更大规模。一个可落地的指标表应至少覆盖 all-reduce、all-gather、reduce-scatter、all-to-all 四类 collective，在 8/16/32/64/128 卡分档统计有效带宽、P50/P99 延迟和扩展效率；MoE 训练要单独测 dispatch/combine 和 expert parallel 的 all-to-all，因为平均 all-reduce 带宽无法代表最热专家造成的尾延迟。

推理场景要换一套语言。Prefill 是算力和内存带宽问题，Decode 是 HBM/KV 和尾延迟问题，MoE 是 expert dispatch/combine 问题，长上下文是 KV reuse/offload 问题，多租户是通信域隔离问题。**这里有一个常被忽略的判断：KV 传输与 EP/TP 在 scale-up 网络上的争用，是尾延迟（排队）问题，而非平均带宽问题。**KV 流量平均占用通常只有个位数百分比，但 NVLink 类 fabric 当前并不普遍暴露按流量类型分级的 QoS 机制；一旦 KV 大块突发砸中正在进行的 dispatch/combine，就会直接推高 decode 的 P99 TPOT。CloudMatrix384 把这件事用三平面隔离掉了——UB 承载异步细粒度 pool 访问，RDMA 承载 P→D 大块 KV 交接，VPC 隔离控制流[\[9\]](https://arxiv.org/html/2506.12708v1)。这类按流量分层的设计，比”单卡 tokens/s”更接近超节点推理的真实瓶颈。

![[超节点南向互联：六条路线、三类哲学与系统契约之争-08.png]]

*图 8：TPU 8t rack 接入 Virgo fabric。8t 走 high-radix、flat two-layer non-blocking 的 scale-out fabric 服务大规模 pre-training，而同代 8i 改用低直径 Boardfly 服务 MoE/reasoning——同一代芯片为训练和推理准备了两套拓扑假设。来源：Google Cloud Blog TPU 8t/8i deep dive。*

**（v3.0 新增）** Google TPU 8t/8i 把”训练指标和推理指标要分开设”这件事，从软件约定升级成了硬件事实。8t 服务大规模 pre-training，继续扩 3D torus 并叠 Virgo scale-out fabric，验收语言是训练 step time、跨 slice 扩展效率和故障恢复；8i 服务 reasoning/serving，改用低直径 Boardfly 把 1024 芯片 Pod 的最大网络直径从 16 跳压到 7 跳，再用 CAE 压低 on-chip collective latency、用更大 SRAM 兜住长上下文 decode 的 KV working set[\[40\]](https://cloud.google.com/blog/products/compute/tpu-8t-and-tpu-8i-technical-deep-dive)。**当一家把全栈攥在手里的厂商，宁可为训练和推理各做一套拓扑也不愿共用一张网，就说明这两类负载对南向互联的要求差异已经大到不能用同一张指标表验收——这正是这一节最硬的外部佐证。**

因此，项目验收指标建议拆成五层：

第一层是硬件链路：单卡 scale-up 带宽、跨柜退化率、512B 小包延迟、光互联距离、误码率、pJ/bit、链路故障检测和保护切换时间。

第二层是通信库：collective primitive 覆盖、拓扑感知 rank mapping、通信组重建时间、链路 degraded 状态下的自动避让、P99 延迟。

第三层是事务与内存语义：是否支持 read/write/atomic、transaction 粒度、地址空间、ordering 和 completion 行为、In-Network Compute 覆盖哪些 primitive。**如果方案声称同时支持 UALink 或其他专用 scale-up fabric，还要单独列出 DL replay 粒度、credit model、flit size——只写”复用 200G Ethernet PHY”不能证明上层 fabric 语义一致[\[35\]](https://miraclefarms.github.io/notes/2026/06/21/ualink-open-scale-up-fabric/)。**Tomahawk Ultra 给出的 51.2 Tbps、250ns、64B line-rate 是交换芯片层的必要条件[\[18\]](https://investors.broadcom.com/news-releases/news-release-details/broadcom-ships-tomahawk-ultra-reimagining-ethernet-switch-hpc)，不能替代端点语义验收。

第四层是训练负载：Dense LLM 和 MoE LLM 的 tokens/s、MFU、扩展效率、checkpoint restore、故障恢复后吞吐下降。

第五层是推理负载：Prefill/Decode tokens/s、TTFT、TPOT、KV block Put/Get、P/D KV 迁移带宽、prefix 命中率、多租户 SLA violation rate。**Scale-up fabric 的最后验收不在链路表格里，而在训练 step time、推理 TPOT 和故障恢复窗口里。**

## 十一、结论

超节点的行业现状可以压成一句话：NVIDIA 已经把 72 GPU NVLink domain 做成成熟产品；华为用 UB 把 384 NPU/CPU/内存池组织成更大的国产超节点，并规划万卡级互联；Google TPU 用 OCS 把拓扑做成可重排资源，并按训练/推理把 8t/8i 拓扑分叉；UALink 在押注开放 memory-semantic pod；SUE/ESUN 把以太网交换生态下沉成 scale-up fabric；国内 GPU 厂商则在 16/64/128/256/512 卡之间寻找工程落点，并开始用国产以太网交换绕开私有互连依赖。**这六条路线的竞争重心，已经从”谁带宽最大”变成”谁能把更大域、更开放生态、更可重排的拓扑、更稳定的运维语义一起交给软件”。**

把四篇深挖综述合到一起，能得出三个更结构化的判断。第一，**底层物理生态正在趋同，系统行为的分野发生在 DL/TL 与拓扑机制两层。**同一代 AI rack 大概率共用相似的 PAM4 SerDes 和光模块，OCI MSA 还会把光互连进一步标准化；真正决定”这是一台机器还是一组连得很快的设备”的，是 data link 的可靠性/流控模型、transaction layer 的内存语义，以及拓扑是焊死的分组交换全互连还是 OCS 那样可重排的电路交换。第二，**短期格局是”性能现货看 NVLink，可重排拓扑看 Google OCS，开放语义看 UALink，交换芯片现货看 SUE/Ethernet”。**NVLink 的工程闭环已经跑通，Google 用 OCS 证明了拓扑可调度是一条独立且已规模生产的路线（代价是只在自家云内可用），UALink 的规格最完整地表达了开放 pod 但产品化仍在 2026-2027 验证期，SUE/Tomahawk 已经把交换芯片送到系统厂商手里。第三，**带宽断崖仍在，但已经出现两类不同的应对。**机柜内 130 TB/s 与跨 domain 约 50 GB/s 之间的三个数量级落差，没有任何已公开路线图能在两年内填平：UALink 和 OCI MSA 试图把跨域地板从 50 GB/s 往上挪，Google OCS 则换了个思路——不填断崖，而是把域内拓扑重排成贴合作业的形状，让”单一逻辑计算机”在固定带宽下被更聪明地切分。但无论哪种，”单一逻辑计算机”的边界短期内仍然是一个 rack 或几个 rack，而不是整个数据中心。

这些判断都有边界。NVIDIA、华为、AMD、Google 的官方材料、TPU v4/NSDI 论文和 OCP/UALink 规范可作强引用；其中 TPU 8t/8i 目前主要来自 2026 年 4 月 Google 官方发布和技术 deep dive，应按”技术预览口径”理解，134,000 chip/fabric、47 Pb/s、100 万 chip logical cluster 等数字尚未进入稳定的 Cloud TPU 版本文档。沐曦、昆仑芯、寒武纪等官网材料能支撑产品形态判断；摩尔线程 C256、昆仑芯天池 256/512、寒武纪下一代规格，以及国产以太网 scale-up 的带宽数字，当前主要来自媒体或厂商设计目标，适合列为待核查线索。正式项目承诺里，只有能回到官方文档、论文、产品手册或联合体确认口径的数字，才应进入验收指标。

下一步更值得追的是两类公开证据：一类是真实 rack 上的训练/推理 benchmark——AMD Helios 这类 72 GPU rack 能否把 TP/EP/MoE/KV 流量稳定跑在一个低尾延迟域内，Astera/Marvell 这类 switch 能否把 In-Network Compute 做成可复现数据；另一类是管理面和互操作——Manageability/compliance 能否让 topology、fault、traffic statistics 进入云厂商控制面，多家 endpoint 能否真正互通。没有这两类材料，超节点容易写成”堆卡叙事”；有了它们，才有可能写成可验收、可交付、可复用的系统方案。第一个能让训练和推理软件相信”它看到的是一台机器”的开放 pod，会比任何一张带宽表格都更说明问题。

### 版本对齐信息

- NVLink / GB200 NVL72：基于 NVIDIA GB200 NVL72 产品页与官方博客，72 GPU / 130 TB/s / 单 GPU 1.8 TB/s；跨 domain 约 50 GB/s 与三个数量级带宽断崖取自前期 NVLink 调研综述。
- 华为 UB / CloudMatrix384：基于 arXiv 2506.12708v1 与华为 2025 全联接大会主旨演讲；三平面、退化 <3%、512B 延迟 1.9/1.2us、EMS 与 90% reuse 下 TTFT -59% 均取自论文，Atlas 950/960 规模为发布会口径。
- UALink：基于 2025-04 UALink 200G 1.0 白皮书与规格概览、2026-01 公开白皮书、2026-04 四规格公告（Common 2.0 / DL/PL 2.0 / Manageability 1.0 / Chiplet 1.0）；93% effective bandwidth、sub-microsecond RTT、1024 accelerator 为规格/路线图口径，硬件出货按 Astera/Marvell 公告分别标注。
- SUE / ESUN：基于 OCP《Scale Up Ethernet》v1.0.0（Approved 2025-09-05）与 OCP ESUN workstream 公告；opaque command channel、AFH/LLR/PFC/CBFC 与五层验收口径取自前期 SUE 调研综述。
- Broadcom Ethernet AI portfolio：基于 Tomahawk Ultra（2025-07-15）、Tomahawk 6（2025-06-03）、Thor Ultra（2025-10-14）与 OFC 2026 portfolio（2026-03-12）公开资料；本文将 Tomahawk Ultra 视为低时延 scale-up 特化分支，Tomahawk 6 视为高带宽 scale-up/scale-out 通用主线，OCI MSA 用作光互连双层战场旁证。
- AMD Helios / HPE Helios：AMD 官方博客与 HPE 2025-12 公告；72 MI455X、260 TB/s aggregate scale-up bandwidth、2.9 FP4 exaflops、31 TB HBM4 为 HPE 公告口径。
- Google TPU / OCS：基于 TPU v4 论文（arXiv 2304.01433）、NSDI 2024《Resiliency at Scale》与 2026-04 TPU 8t/8i 技术 deep dive；4x4x4 cube / 6144 optical ICI links / 48 OCS / twisted torus +~70% bisection、OCS <5% 成本 <3% 功耗为论文口径，Boardfly 16→7 跳、CAE -5x collective latency、Virgo 134,000 chip/47 Pb/s/100 万 chip logical cluster 为 8t/8i deep dive 口径，TPU 8 按技术预览口径使用。
- 国产超节点：沐曦 64 GPU 3D Mesh / 128 GPU 单柜 / 16-64 GPU 光互连、昆仑芯 P800 OAM 与 IB/RoCE 万卡集群、寒武纪思元 370 MLU-Link 为官网可引用口径；摩尔线程 C256、昆仑芯天池 256/512、寒武纪 590/690/790 与国产以太网 scale-up 带宽数字为媒体/厂商设计目标，标注待核查。
