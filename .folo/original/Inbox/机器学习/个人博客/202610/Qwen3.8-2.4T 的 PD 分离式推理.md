# Qwen3.8-2.4T 的 PD 分离式推理

> [!info] 个人博客 · Inbox · 2026-10-09 18:18 · [原文](https://mp.weixin.qq.com/s/deeMa7CXwqZwmfPsnvSvfQ)

## 摘要

本文介绍了我们在 GB300 NVL72 集群上，使用 vLLM 为 Qwen3.8-2.4T 模型提供 Prefill/Decode 分离式推理服务（简称 PD 分离），在 8K 输入、1K 输出工作负载下取得的最新性能结果。在高吞吐场景中，vLLM 实现了每 GPU 每秒 **5000** token 的总吞吐量；在低延迟场景中，每用户每秒可生成 **180** 个 token。这两个结果都展示在下文的帕累托前沿中。我们将详细解释如何取得这些结果，并提供具体的 srt-slurm 配置方案，让大家能够通过本地部署自行验证和复现。更重要的是，我们会介绍制定这些配置方案时的决策过程。这比性能数字本身更有价值，因为它能帮助你在 vLLM 上为任意模型调优 PD 分离式服务，充分挖掘性能。

## 引言

不久前，我们公布了 Qwen3.5 PD 分离式推理服务的测试结果，展示了 vLLM 如何达到每 GPU 每秒 2.5 万 token 的总吞吐量。紧接着，Qwen 家族又发布了新的前沿模型 Qwen3.8-2.4T。本文将目光转向 Qwen3.8-2.4T 的 PD 分离式推理服务，并展示完整的帕累托前沿。

在此前的 Qwen3.5 研究中，我们主要关注帕累托曲线的左侧，目标是最大化每 GPU 的总 token 吞吐量（Total TPS/GPU）。这一次，我们进一步构建完整的帕累托前沿，同时覆盖左侧的高吞吐区域和右侧的低延迟区域。换句话说，除了面向吞吐量的配置，我们还会找出能够最大化交互速度，即每用户生成 token 速率（Gen TPS per user）的最优 PD 配置方案。

同样重要的是，本文不只展示最终数字，还会逐步拆解调优过程：如何选择测量对象、如何识别瓶颈，以及如何通过迭代获得更好的 PD 配置。我们的目标是让这套流程易于理解和复用，帮助大家调优其他模型的推理服务性能。

## 最大化吞吐量

我们首先要最大化的指标，是每 GPU 的总 token 吞吐量。这个指标取决于并发数：一个解码引擎同时服务的请求越多，吞吐量就越高。

限制并发数的是 KV 缓存容量，因为每个活跃请求都会占用其中一部分。因此，无论采用哪种拓扑，首先都需要弄清楚 KV 缓存的大小。这个问题又可以拆成两部分：单个请求会消耗多少缓存，以及加载模型权重、为 vLLM 服务自身运行分配空间之后，GPU 上还剩多少空间可用。本节将分别分析这两部分，进而估算 Qwen3.8-2.4T 在单块 GB300 上理论可达的最大并发数。

### 估算单个请求的 KV 缓存占用

Qwen3.8-2.4T 共包含 92 层，其中有 69 个 GDN 层和 23 个全注意力（Full-Attn）层，每一层都有一个 MoE 模块（92 × 512 个专家）。GDN 和 Full-Attn 使用 BF16，MoE 使用 NVFP4。权重可分为以下两类：

- • 91 GiB：模型的非专家权重，其中 GDN 权重占 60 GiB，Full-Attn 权重占 19 GiB。

- • 1242 GiB：模型的专家权重。

Qwen3.8-2.4T 是一个混合架构模型，因此其状态分为两部分，而且两者的空间计算方式截然不同：Full-Attn 状态随 token 数量增长，而 GDN 状态按请求存储。

Full-Attn 状态按 token 存储。每个 token 在每一层需要 2 KiB：

![[Qwen3.8-2.4T 的 PD 分离式推理-01.png]]

每个 token 的 Full-Attn 状态：num\_key\_value\_heads 为 4，乘以 head\_dim 256，再乘以 float8\_e4m3fn 的 1 字节，最后乘以 K 和 V 两份，得到 2048 B，即 2 KiB。

GDN 状态是**按请求**存储的，而不是按 token 存储，这一点很关键。它由两部分组成。

- • 卷积状态（Conv state）：保存因果卷积最近的 kernel−1 个输入，每个通道对应一个滤波器，通道由 q、k、v 拼接而成：

![[Qwen3.8-2.4T 的 PD 分离式推理-02.png]]

每个请求的 GDN 卷积状态：q 和 k 部分为 linear\_key\_head\_dim 128 × linear\_num\_key\_heads 16 × 2，再加上 v 部分的 linear\_value\_head\_dim 128 × linear\_num\_value\_heads 128；整体乘以 linear\_conv\_kernel\_dim 减 1（即 3），再乘以 bfloat16 的 2 字节，得到 122,880 B，即 120 KiB。

- • SSM 状态：承载完整上下文信息的递归矩阵：

- 

![[Qwen3.8-2.4T 的 PD 分离式推理-03.png]]

每个请求的 GDN SSM 状态：linear\_num\_value\_heads 128 × linear\_value\_head\_dim 128 × linear\_key\_head\_dim 128，再乘以 bfloat16 的 2 字节，得到 4,194,304 B，即 4 MiB。

两者相加，GDN 状态需要 4 MiB + 120 KiB = 4216 KiB。

vLLM 以块为单位分配 KV 缓存，每个块必须足够大，能够容纳一个 GDN 状态，或若干个 Full-Attn 状态。对于 Qwen3.8-2.4T，GDN 状态的大小是单个 Full-Attn 状态的 `4216 KiB / 2 KiB = 2108` 倍。因此，块大小由 GDN 状态决定，并按 16 字节对齐，即每个块可容纳 `align(2108, 16) = 132 * 16 = 2112` 个 token，对应的块大小为 `2112 × 2 KiB = 4.125 MiB`。

在分离式推理服务中，需要注意：prefill 和 decode 会各自独立计算块大小，但 KV 缓存传输要求两侧的块大小一致。如果不一致，就需要手动设置 `--block-size`，确保这个值足以在两侧容纳 GDN 状态，代价是浪费一部分 KV 缓存空间。

算出单个块的大小之后，我们就能计算一个完整请求会占用多少 KV 缓存，并据此估算测试中可能达到的最大并发数。这个计算需要先估计工作负载。我们固定输入序列长度 ISL=8192、输出序列长度 OSL=1024，也就是所谓的长输入、解码受限测试场景。

KV 缓存使用的是加载模型并完成所有其他空间预留后剩余的 GPU 显存，因此首先需要厘清所有显存占用项。

### KV 缓存容量

GB300 最初提供 279 GB 显存。驱动开销先占用 2.28 GiB，因此 vLLM 启动时的显存总量为 276.62 GiB。在 vLLM 服务启动之前，CUDA 上下文已经占用了约 3.13 GiB。这部分显存完全不受我们控制，也无法调整。

此外，vLLM 默认会从 276.62 GiB 的基准容量中预留 8%，用于应对无法提前预测的情况，例如激活显存峰值以及类似影响。`gpu_memory_utilization` 参数控制的就是这一项。扣除这部分预留后，大约还剩 254 GiB。

NCCL 缓冲区、内存分配器以及其他非 PyTorch 组件还会占用 2.90 GiB。因此，在加载权重之前，我们剩下的空间为 `276.62 × 0.92 − 3.13 − 2.90 = 248 GiB`。

#### 激活显存峰值

加载权重后，vLLM 会测量模型在 eager 模式下执行一个步骤需要多少显存，也就是不使用 CUDA Graph 的情况。这一步很有必要，因为 CUDA Graph 本身有一个最大规模限制，而推理时的批大小可能超过这一上限。即便如此，我们仍然需要执行这次前向传播，此时就必须使用 eager 模式。当然，这类情况会导致性能下降，应当尽量避免，但在实际运行中无法保证它永远不会发生。eager 模式的前向传播会使用 `max_num_batched_tokens` 个 token，以便测出最坏情况下的激活显存峰值。

估算显存占用最简单的方法，是针对你关注的 decode 拓扑，在 prefill 与 decode 合并部署的模式下进行几次测试。对于本文涉及的拓扑，我们测得每个引擎的激活显存峰值如下：

#### CUDA Graph

接下来，vLLM 会捕获 CUDA Graph。图所需的显存必须预先分配在固定地址上，这意味着必须在捕获图**之前**估算它所需的显存。

截至本文撰写时，vLLM 的实现方式如下。首先，枚举当前服务配置下所有可用的图规模。一次只能重放一张图，而图越大，显存峰值占用也越高，因此至少要为最大的图留出足够空间。接下来需要确定其余图还需要多少额外显存。这一点与 eager 执行不同：图一旦完成捕获，后续重放就会复用完全相同的地址。再捕获第二大的图，就会发现它在第一张图已占用的显存之外，还需要额外占用一部分显存，记为 。

为了节省预热时间，vLLM 随后作出一个假设：之后每多捕获一张图，都会增加同样大小的 。因此，CUDA Graph 所需显存按  计算，其中  是最大图的显存占用， 是图的总数。由于图使用固定地址，而且我们无法在启动时捕获所有图，因此必须根据这一估算值，提前预留全部空间。

实际中，估算值往往大幅高于图真正需要的显存。如果想自行测量，可以在合并部署模式下测试 decode 拓扑，使用 `compilation-config: '{"cudagraph_mode": "FULL_DECODE_ONLY"}'`，并设置 `max-cudagraph-capture-size`。

这张表也清楚说明了为什么需要通过 `gpu_memory_utilization` 预留显存。在某些测试中，图的实际显存占用超过了初始估算，而额外预留的空间正是避免这类情况演变为显存不足（OOM）的保障。

需要注意，留给 KV 缓存的空间取决于 CUDA Graph 的**估算占用**，而不是图在运行时的实际占用，因此 KV 缓存大小直接受估算准确度影响。在我们的测试中，这一估算总体上是合理的，但如果你希望挖掘最后几个百分点的优化空间，可能需要手动估算图的大小。vLLM 的图显存估算机制值得进一步研究和改进，因为随着 Qwen3.8、Kimi-K3 和 DSV4 等万亿参数以上的前沿模型出现，这个问题变得越来越迫切。

## 测量 Prefill 性能

接下来一个重要步骤，是将 prefill 与 decode 分开测量。这意味着在合并部署的服务上运行仅针对 prefill 的工作负载，即 ISL/OSL=8192/2。这样就能确定在分离式服务中，prefill 端应该选择哪种拓扑。分别测量 prefill 和 decode 工作负载，可以帮助我们选出最佳拓扑，并显著减少测量 PD 分离式服务性能所需的工作量。我们为 prefill 选择了以下拓扑进行测试：

- • TP4DP2+EP

- • TP2DP4+EP

- • TP4DP4+EP

- • TP2DP8+EP

- • DP16+EP

- • TP1PP6+EP

- • TP1PP8+EP

- • TP8+EP

- • TP16+EP

## 测量 Decode 性能

对于 decode，我们采用同样的方法：在合并部署的服务上运行仅针对 decode 的工作负载，即 ISL/OSL=1/1000。我们选择了以下拓扑：

- • TP2DP4+EP

- • TP4DP8+EP

- • TEP8

- • TEP16

此外，我们还尝试启用 MTP，并设置 3 个推测 token，以期获得更好的性能。

## 结语
